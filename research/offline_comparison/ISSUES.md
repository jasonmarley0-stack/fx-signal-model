# Consolidated issue list — offline strategy comparison milestone

One list, as requested, covering defects found and fixed during this milestone, deliberate scope boundaries, and deferred items for a later iteration. Nothing here was allowed to expand this milestone's scope (three candidates, one fixed rule set each, no parameter sweep).

## Fixed during this milestone (compromised the experiment if left)

1. **`by_month()` silently omitted zero-opportunity months.** The first version only emitted a row for a month that actually had an issued alert — a candidate that went quiet for a calendar month would simply be missing from the table rather than showing a zero row, contradicting the explicit requirement to show zero-opportunity months. Fixed to always emit every month in `[period_start, period_end]`, zero-filled where nothing fired. (No zero-opportunity month actually occurred in this dataset for any candidate, but the fix is required regardless — the table must not depend on getting lucky.)
2. **`classify_and_record()` had no way to set a non-default entry-validity window.** `configs.py` documents `ENTRY_VALIDITY_HOURS = 4.0`, but `src/alert_lifecycle.py`'s `classify_and_record()` only ever called `guarded_entry_expiry()` with its hardcoded 90-minute default — every replay alert would have silently used 90 minutes regardless of what the contract said. Added an `entry_validity_minutes` parameter (default unchanged at `DEFAULT_ENTRY_VALIDITY_MINUTES`, so the live scanner's behaviour is untouched), threaded through from `replay_engine.py`. Re-ran the full pre-existing `alert-lifecycle-prospective-scoring` test suite (5 files) after this change — all still pass.

## Deliberate scope boundaries (not defects — stated so they aren't mistaken for oversights)

3. **Position-open suppression is total, not partial.** While a pair has an open (assumed-entered, unresolved) position under a given candidate, this replay evaluates *nothing* for that pair — no cosmetic no-op, no revision, no cancellation bookkeeping — until the position resolves. The live scanner's actual lifecycle code continues polling and would still record e.g. a cancellation during that window (with existing-position guidance, per the already-built requirement 4). This replay's simplification is coarser and was a deliberate choice for this milestone's position-accounting needs; a future iteration that wants to study "what did the alert feed say *while* a subscriber was holding a position" would need to relax this.
4. **Sensitivity was run on two dimensions only** (real bid/ask vs. zero-cost mid; +30 minutes of execution delay) — not `ENTRY_TOLERANCE_ATR_MULTIPLE`, not `MAX_HOLDING_TIME_HOURS`, not the confidence thresholds. Widening this is a parameter sweep, explicitly out of scope for this milestone.
5. **Outcome/exit checking uses M30 candle resolution**, matching `performance_scorer.py`'s own existing precedent, not tick data — this is a stated resolution limit, not an attempt to approximate tick-level fills.

## Deferred for a later iteration (recorded, not actioned here)

6. **`incomplete_coverage` is concentrated around weekend gaps.** `MAX_HOLDING_TIME_HOURS=30` frequently lands the holding boundary inside the Friday-evening-to-Sunday-evening FX market closure, especially for entries confirmed Thursday/Friday. This is real, correctly-handled behaviour (no price is fabricated) but is worth revisiting — e.g. whether a holding-time exit should be defined in trading hours rather than wall-clock hours — before a future milestone tightens the unknown-outcome band.
7. **`insufficient_data_entry` is the largest single unknown-outcome category** (price touched the entry condition but no M30 bar's own open ever confirmed a price inside it) across all three candidates. A finer entry-checking granularity (M1/M5) would likely reduce this substantially but was not fetched for this milestone — a real, named next step if narrowing the unknown-outcome band becomes the priority, not a defect in the current M30-based contract.
8. **Sample sizes are modest in the holdout period for some candidates** (baseline: 46 entries / 36 resolved). Real, stated in RESULTS.md's recommendation section — not treated as settled evidence either way.
9. **`replay_scorer.py` duplicates `src/alert_scorer.py`'s state machine** rather than parameterising the production module to accept bid/ask series. This was deliberate (an isolated research harness should not risk destabilising the shared production scoring code for a one-off research need) but means a future fix to `alert_scorer.py`'s entry/exit logic would need to be mirrored here by hand if this harness is reused for a later milestone.
